**Purpose of document**

This document outlines the current state of end-to-end (e2e) tests in Accredited Programmes in Community, and describes the next-step options available for the team.  It suggests what needs to happen next.

The document exists to allow the whole team (technical and non-technical) make an informed decision about some work which should happen in the next 4-6 weeks.

**Summary**

Our e2e suite (Playwright in a dedicated repo) runs on every PR against `main` in the UI and API repos, but a failing run no longer blocks deployment — that gate was disabled at some point, most likely due to flakiness, and failures have since been sporadically fixed rather than acted on. The suite only covers "core" flows with no external data dependency; anything touching a Referral needs a POP with an offence in nDelius, which we can't currently generate outside a dev's local machine, despite the Data Generators repo existing for exactly that purpose. **Current status**

We have our end-to-end (e2e) tests in their own dedicated repo ([link](https://github.com/ministryofjustice/hmpps-accredited-programmes-e2e)).  Our e2e tests are written in Playwright.  Right now they only cover a small number of "core" workflows (i.e. flows that do not rely on any data generated by systems *outside* of our own, notably a Referral which would require a Person on Probation (POP) with an offence, and an OASys assessment).

When a PR is raised against `main` in either our API or our UI codebase, we run the e2e test suite.  Theses tests used to block deployments to Dev environment (and onwards to preprod and prod) but that has been disabled, i.e. the e2e tests run, can fail, and we can still deploy latest versions of our codebase to dev.  We did not make a team-wide decision to do this, but I believe it was done because of flaky tests (i.e. tests which failed for no clear reason, and would pass on re-run without making any material changes to the code).  The tests have been failing on-and-off for a while, and our devs (usually Alison) have been sporadically fixing them.

Although we have in-code ability to create POPs (and offences, assessments) using the [test-data-generator](https://github.com/ministryofjustice/hmpps-accredited-programmes-test-data-generators) repo, which we use for e.g. manual testing and demos in dev, these don't run before our e2e tests. I.e. we have no way to programatically create (or clear-up) POPs in our system ahead of test runs.

We have a series of tickets lined up to the incoming sprint (89):

* [APG-2041](https://dsdmoj.atlassian.net/browse/APG-2041)
* [APG-2029](https://dsdmoj.atlassian.net/browse/APG-2029)
* [APG-2042](https://dsdmoj.atlassian.net/browse/APG-2042) (Adding a Referral to a Group)

Which are about creating end-to-end tests around the viewing (and searching) for a Group in our system (this is an internal entity, with no dependencies on other systems).  However adding a Referral to a Group would require the existence of a Referral, which would require creation of a PoP in nDelius.  

**The Problem**

The ask to extend out e2e test suite raises the basic question "why bother?"

Given the current state of our e2e test suite, we may not see meaningful improvements to our team's reliability (i.e. chance of accidentally breaking core user flows through our system, or to a lesser degree of shipping new features which break) without, possibly significant, other changes.

The core of the problem is that we simply don't do anything with end-to-end test failures.  I.e. if an e2e test run fails, devs are able to continue a merge of code to `main` and therefore deployments (to dev, preprod, prod) .

Although we could turn this feature on, i.e. block all deployments without a successful e2e test run, doing so would almost certainly do more harm than good for team performance (discussed below). 

Therefore, in order to pragmatically improve team productivity and reliability, we likely need to make an informed decision about how we can incrementally improve the team tooling, without sinking a lot of dev-hours into tooling, which may be better spent on feature development.

**Technical Complications**

I want to briefly outline some of the complicating technical factors.  Non-technical readers are encouraged to skim or skip this.  Technical readers are therefore encouraged to engage more deeply to ensure we're being sensible. 

**Cross-repo GitHub Action authentication**.  There are a number of interconnected GitHub repositories.  The Data Generators would be required by the E2E tests, whcih would be required by both the UI and API repositories.  I.e. there is a grandparent -> parent -> child relationship.  This would require a considered GitHub authentication pattern which, in the post-LAA incident world, we do not have.

**Long-running processes.** The time to run the Data Generators would likely exceed 10 minutes to generate a single Referral.  It is conceivable that multiple Referrals could be needed by multiple runs of tests, as the sharing of data may not be possible.

**No single source of e2e test failure.**  Failures at the end-to-end level can be legitimately caused by changes we make to _either_ our own UI or API repos; they can also be caused by changes (or outages, performance issues, etc.) in shared up-stream systems, e.g. nDelius, OASys

**Flaky tests and the cost of re-runs.**  The existence of slow, and historically flaky tests, suggests that blocking a merge to `main` (and therefore a deploy to any environment) risks slowing down our release cadence, causing organisational pain and counter-intuitively, reducing our ability to respond to failures and outages.

**Historically low levels of failure.**  Although not strictly technical, I want to acknowledge that the team has a history of collaboration and high level performance, as well as two relatively comprehensive unit testing suites in both repos.  Excepting some recent cross-repo (i.e. UI and API) changes, i.e. multiple PDU filters, the team has a record of continuous deployment and low level of regression.  This factors into the cost-benefit when trading off the need for strict, thorough, automated e2e testing.

**Historic issues with integrations.**  We have experienced a lot of issues with nDelius-level integrations, more than our own "core" workflows.  This includes issues with (re)scheduling appointments, and the submission of notes.  Unfortunately, this kind of cross-platform checking (i.e. logging into M&D, then checking on M&D) would require a significant investment in our codebase, but it could almost certainly offer us demonstrable value.

**The Ask**

As a team, I think we need to make two decisions:

1. When do we want to run our e2e test suite, and what do we want to do with the failures?
2. When do we want to introduce tests on features which rely on external data (namely Referrals)?

These decisions can be made independently, and can be incrementally implemented.  I suspect we'll need to do both, to some degree.

**When do we want to run our e2e test suite?**

Right now our e2e test suite runs on merge to `main` but failures are ignorable. 

We could pragmatically move our test suite to run nightly.

Moving to a nightly cadence, combined with a greater team focus, and response to, the Slack alerting we already have configured, lets us reduce the noise of test failures on every PR and increase the signal. 

An alternative is continuing to run the full suite on every merge to `main` and treating a failed run as an *actual* blocker, i.e. code cannot be deployed without a successful e2e run.  Although this is the theoretically "proper" answer, it would incur significant cost in both initial investment, and we're still at the whims of system-level problems (e.g. what if nDelius actually ships a change, what if we time out on an OASys request?) 

**When do we want to introduce tests on features which rely on external data (namely Referrals)?**

There's obvious value here for the team, but I think we need to acknowledge it's more work than we've currently got scoped in the above-mentioned tickets.  I think we should do this work, but possibly in its own sprint, to make sure we can improve what we have.

The previously-written APG-2042 assumes a Referral already exists (and can be added to a Group).  Although devs can currently achieve this on their local machines, using the Data Generator repo, we have yet to do this in an automated environment (like a CI pipeline).  I think we should dedicate some devs in a sprint to get a PoC of that flow working to see if it's possible.  We could create a pretty basic test for finding a Referral via CRN then viewing the Referral details after this work is completed.
